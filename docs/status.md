## 验证边界

- 安装、文件系统检查和 sparse 往返比较先在电脑完成，随后才写设备。
- 实际验证了桌面、单指点击/滑动、返回应用列表、Wi-Fi 和正常重启。
- 先后经历 GNOME GPU 故障、纯软件 Phosh，再启用保守的 GPU 合成。
- GPU 限制 devfreq 目标为 320MHz；`cur_freq` 曾采到 320/465/320MHz，不能宣称始终硬锁 320MHz。
- 多点槽位在代码中实现，但本轮使用者主要验证单指；不保证十指、掌触、压力或手写笔。
- 深度休眠仍禁用；音频播放/录音、相机、传感器、硬件视频解码、Vulkan 和可靠充电/续航没有完整测试。蓝牙的已通过与未验证部分单列如下。
- 图形应用仍使用软件绘图，GPU 合成成功不等于所有应用已硬件加速。
- 应用启动补丁通过重新建立桌面会话实测；未为该用户态补丁再次刷写或重启整机。
- 后续发现普通熄屏也会影响TDDI触控，禁用整机深度休眠并不足以覆盖它。已新增保留input设备的暂停/恢复控制和亮屏恢复服务。软件关闭输出的三轮测试只验证恢复路径，未涵盖密码解锁，且旧会话出现Phosh锁屏/monitor引用失配；清理后，用户完成实体电源键、密码解锁及打开设置验证。没有为这次修复再次重启整机，长期休眠仍不宣称可用。
- 蓝牙已完成外部UART、版本回复、固件加载、扫描、实际配对/连接及重启后再次连接；开机自动初始化、原厂身份和配对/信任记录保留。修复GPIO11被唤醒IRQ改回普通GPIO的问题，且为通用NVM补回本机原厂地址。自动重连、实际音频播放、所有BLE外设及深度休眠唤醒未验证，见[蓝牙记录](bluetooth.md)。`CONFIG_BT_LE`未启用不能据此断言完全没有BLE；在本匹配源码中主要影响ISO。
- 后续运行中诊断确认后摄为S5K4H7、读出CSID/TFE/BUS硬件版本；8个媒体核心模块加载/卸载通过。UART FIFO空接收函数错误、CAMSS供电别名空参数Oops及恢复过程保留在[早期诊断](bluetooth-camera.md)。相机仍没有可用video/media采集路径。
- 蓝牙修复后的正常重启中，USB控制台自动恢复，蓝牙约17.38秒就绪，桌面/触控/Wi-Fi服务正常且无failed unit。公开UART源码额外加入退役模式入口保护，仅在电脑编译检查，不能与实机原型二进制混为同一产物。
